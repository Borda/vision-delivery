# Delivery Threat Model

Deliver mode runs a chain of helpers. This page says what the chain defends against, what it cannot defend against, and which step does what. To learn whether one delivery passes its checks, run `resources/scripts/check_delivery.py`; it runs the checks below in order, reads files only, and stops at the first failure.

Passed checks do not show two things. They do not show that the scored predictions came from the delivered artifact, and nothing is signed. `check_delivery.py` states both limits on its plain line and in its JSON `not_shown` list.

## Adversary

The adversary is agent drift and overclaiming: an agent, or a hurried person, that skips a step, reports a pass it did not measure, scores against a changed target, or hands off an artifact that differs from the one checked. It is careless or optimistic. It is not a malicious user with the same account.

## Assets

- The frozen acceptance: metric, comparator, threshold, dataset digest, and model.
- The scored baseline result and its 95% interval verdict.
- The artifact tree that is handed off.
- The recorded check outcomes: self-test evidence, the delivery-check contract, and live or offline evidence.
- The handoff record, the ledger proof rows, the economics binding, and the decision report.

## Threats in scope

- **T1 Skipped step.** A required step never ran, or ran for another acceptance revision.
- **T2 Unmeasured pass.** A pass is reported without a measurement that supports it: a self-declared `passed`, a verdict other than `pass`, a point estimate with no interval, or a baseline record whose numbers its label and prediction files do not reproduce.
- **T3 Moved target.** The result is scored or checked against a target, dataset, or output oracle that changed after the result was known, or a record carries a top-level target that disagrees with the target the scorer applied.
- **T4 Swapped artifact.** The handed-off artifact, command, or kind differs from the one checked.
- **T5 Overclaimed kind.** A scaffold is called delivered, or a hosted client is called local.

## Threats out of scope

- **Same-user forgery.** Nothing is signed. Anyone with the account can write evidence files, ledger rows, digests, and label and prediction files that score as wanted, and every check will agree.
- **A compromised machine.** A changed Python interpreter, helper script, or operating system can report anything.
- **Hostile generated code.** The helpers block Python networking and strip credential variables, but they are not an operating-system sandbox.
- **Clock tampering.** Time checks reject only records dated before the acceptance or more than five minutes in the future.
- **Which model wrote the predictions.** The scorer binds the prediction and gold file digests, not the model or the artifact that wrote the predictions. Passed checks do not show that the scored predictions came from the delivered artifact.
- **Wrong gold labels.** Independent labeling is a methodology rule, not a check.

`check_delivery.py` runs the steps in this order: `acceptance`, `baseline`, `handoff`, `self-test`, `check-contract`, `live-check`, `economics`, `ledger`, `later-records`, `report`. The handoff comes before the evidence steps because it names the evidence files.

No chain step is cut: each one defends an in-scope threat. Running `validate_delivery_handoff.py` and `validate_proof_chain.py` to answer "do the delivery checks pass" is merged into `check_delivery.py`; both scripts stay for their own uses.

## Decisions

- **Only scorer evidence is a baseline, and it is scored again.** A baseline is a record with a `target` block, `task`, `gold_sha256`, and `pred_sha256`; any other record is refused. The `baseline` step finds the label file and the prediction file by those digests, in `.vision-delivery/` or through `--gold` and `--pred`, and runs the scorer's own functions on them in process. Metric, verdict, numerator, denominator, observed value, both interval bounds, missing predictions, and image count must equal the record. A hand-written pass, a changed count, or an interval the files do not produce fails (T2). When the files are not found, the step fails.
- **The scorer's target wins.** Binding fields are read only from the `target` block. A top-level target field or `dataset_sha256` that disagrees with it is refused (T3). The `gold_sha256` must equal the acceptance `dataset_sha256`, so freeze `--dataset-sha256` as the SHA-256 of the gold label file.
- **Only `pass` counts.** A verdict other than `pass`, or a `pass` without its interval bound, is refused (T2).
- **Later records count.** A failed, timed-out, cancelled, or unknown run of a proof action after its last success fails the `later-records` step. So does a latest recheck that scored below the target. The ledger helper binds digests only on successful rows, so a later row that names no acceptance counts against every acceptance.
- **A scaffold never passes the delivery checks.** It has no frozen live or offline check, so `check_delivery.py` stops at `check-contract` (T5).
- **The entry command verifies recorded outcomes only.** It never runs artifact code and never performs a `--execute-reviewed` step. It runs the scorer's functions, which are not artifact code. Its imports include `subprocess` through the scorer's freeze module, but it starts no child process, and it writes no bytecode cache next to its helpers.
